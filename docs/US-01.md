# US-01: Import OULAD activity data

As an analyst, I want to import OULAD activity data so that I can analyze a reproducible course dataset.

Tracks [issue #1](https://github.com/Toladipo0115/COSC565-Software-Engineering-/issues/1), requirement FR-01.

## Setup and usage

Use Python 3.11 or newer. This story uses only the Python standard library; there are no third-party dependencies to install. Run commands from the repository root.

```sh
python -m engagetrace import --input-dir examples/oulad-synthetic --database data/demo.sqlite3
python -m unittest discover -s tests -v
```

The example contains invented records, not research evidence. A successful first import prints JSON with status `STAGED`, a dataset version ID, timestamp, per-file SHA-256 checksum, byte size and row count, and a total of six staged records (1 course, 2 registrations, 3 events). Repeating it returns `already_imported: true` and the same ID and timestamp without adding rows. Deleting `sum_click` from a copy of the event file produces a clear error on stderr and exit code 2.

For real inputs, point `--input-dir` to a local directory containing `courses.csv`, `studentRegistration.csv` and `studentVle.csv`. Their required columns are defined in `engagetrace/importer.py` and Requirements.md. UTF-8 with or without a BOM is supported. Extra columns are ignored, including `id_site`; optional studentInfo.csv is not read. Only the declared detection input fields are persisted. Keep original source files locally for audit and reproduction. Public OULAD data should retain its CC BY 4.0 attribution (Kuzilek, Hlosta and Zdrahal, Open University Learning Analytics Dataset).

The default is 100 MiB per file. Full studentVle.csv may exceed that proposed prototype limit; explicitly raise it with `--max-file-mb 1024` when appropriate. Parsing is streamed; temporary source snapshots use disk proportional to the input size. SQLite staging also uses disk. No original datasets or generated database files should be committed. SQLite and CSV inputs remain local; this command starts no network service.

## Persistence and failure behavior

The dataset ID hashes a sorted manifest of input checksums, sizes and the staging-policy version. Paths and timestamps are excluded, so copying identical inputs to another directory preserves identity. A private temporary snapshot ensures each stored checksum describes the bytes actually parsed. Those temporary files are removed after the operation. SQLite stores a manifest and the projected input records in staging tables, with foreign keys enabled. A single transaction publishes the complete dataset; a malformed later file rolls back earlier inserted records. An existing completed staged dataset is never changed by a failed subsequent import. Failed attempts return a nonzero exit code and do not create a published dataset version; a separate failure-audit table is outside US-01.

## Story boundary

`STAGED` means structurally imported, not validated for detection. Row counts are staged records, not claims of semantically accepted student activity. Missing required columns, malformed CSV, missing files, invalid encoding, empty datasets and file limits are checked here. Required fields are retained as source strings, including blank registration dates. Numeric/range/reference validation, rejected-row reports, course-week aggregation, coverage and enrollment eligibility policy belong to US-02. No zero filling, detectors, React dashboard, API or experimental claims are added by this story. Later stories can migrate staging data into the normalized domain tables in Requirements.md without altering the source manifest.

## Acceptance evidence

Tests cover the persisted manifest and projected records, repeat imports, stable identity across paths, changed-input versions, required columns in each file, failure rollback, existing-data preservation, BOM, ignored extra fields, empty inputs, file limits, and CLI success/error exit codes. These fixtures test import behavior only. Conference experiments and held-out validation remain pending.
